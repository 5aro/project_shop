# 지원서와 면접에 활용하기

## 프로젝트 소개 초안

“합성 이커머스 주문·결제·배송 데이터를 수집하여 PostgreSQL 정산 원장을 구성한 데이터 엔지니어링 프로젝트입니다. 이벤트 중복, 늦은 환불, 잘못된 수량을 포함한 시나리오에서 멱등 적재와 트랜잭션 롤백을 검증하고 Airflow DAG와 대시보드로 처리 결과를 확인했습니다.”

완성본은 AI의 도움으로 작성되었습니다. 먼저 실행·수정·검증하며 이해한 범위만 본인의 역량으로 설명하세요. 혼자 전부 설계·구현했다거나 실서비스 매출을 개선했다는 표현은 사용하지 않습니다. 학습 후 본인이 변경한 내용과 그 근거를 별도 기록하면 좋습니다.

## 이력서 문장 후보 — 이해하고 재현한 뒤 사용

- 합성 주문 6,000건·34개 수신일 파티션의 수집 및 정산 파이프라인을 재현하고, 원장과 독립 정답 합계의 일치를 검증.
- 이벤트 ID·해시·배치 체크포인트를 이용한 멱등 적재와 늦은 환불 반영, 실패 롤백을 통합 테스트로 확인.
- Pandas/Polars/Dask의 20만 행 집계를 동일 결과 조건으로 비교하고 실행 시간·peak RSS·측정 한계를 기록.

## 5분 시연

0:00 문제: 중복 결제와 늦은 환불이 집계를 왜곡한다.
0:40 대시보드에서 6,000건·순수납액·격리 31건을 확인한다.
1:30 아키텍처와 수신일/주문일 구분을 설명한다.
2:20 `python -m shopscope verify`와 테스트 결과를 보여준다.
3:10 재실행 불변성과 JOIN 전 사전 집계 코드를 설명한다.
4:10 실제 벤치마크·잘못된 의미 검색 사례와 MongoDB 미검증 범위를 보여준다.
4:40 다음 개선: 영향 날짜만 마트 갱신, 외부 원장 대조, 접근 권한 분리.

## 면접 질문과 핵심 답

| 질문 | 설명할 내용 |
|---|---|
| 왜 이 주제인가? | 데이터 엔지니어의 수집·정합성·운영을 하나의 금액 흐름으로 검증 가능 |
| 왜 PostgreSQL인가? | 원장 관계, 제약, 트랜잭션, SQL 집계 |
| ETL인가 ELT인가? | Python에서 형식 검증 후 적재하고 DB에서 마트 변환하는 혼합 구조 |
| 멱등성이란? | 동일 입력을 다시 적용해도 업무 결과가 바뀌지 않음 |
| 정확히 한 번 처리인가? | 분산 exactly-once를 주장하지 않음; 재시도와 중복 통제를 구현 |
| 왜 먼저 GROUP BY인가? | 결제와 배송 다중 행 JOIN의 곱셈 중복 방지 |
| 늦은 환불은? | 수신 파티션으로 수집하고 과거 주문 코호트를 재계산 |
| 품질 5%는 근거가 있는가? | 합성 시나리오용 정책값; 실무에서는 SLA·비용으로 합의 필요 |
| Dask가 느린 이유는? | 작은 데이터에서 작업 준비 비용, 병렬화의 고정 비용 |
| 벡터 검색이 틀리면? | 소규모 질의 사례 분석, 더 넓은 평가셋, 모델·필터 선택 재검토 |
| 가장 큰 한계는? | 합성·소규모·단일 머신, 전체 마트 재계산, 실제 운영 미검증 |
| 본인이 한 일은? | AI 도움과 본인이 재현·수정·검증한 범위를 구체적으로 구분 |
