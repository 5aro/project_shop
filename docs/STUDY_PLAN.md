# 완성본을 공부하는 6주 계획

주 5일, 하루 60~90분을 권장합니다. 1일차 읽기, 2일차 실행, 3일차 손으로 검산, 4일차 작은 변경, 5일차 설명 녹음을 반복합니다. 새로운 기능을 많이 추가하기보다 기존 결과를 설명하는 데 집중합니다.

| 주 | 읽고 실행할 내용 | 직접 할 일 | 통과 기준 |
|---|---|---|---|
| 1 | README, CODE_TOUR 1~4, generate/collect/quality | 주문 한 건을 JSON→raw 파일까지 추적; 함수·dict·예외 설명 | 입력과 출력, 실패 사유를 말할 수 있음 |
| 2 | 스키마와 분석 SQL, order_finance | JOIN 전후 행 수 계산; 채널별 순수납액·순위 직접 조회 | GMV/결제/환불/순수납 구분, JOIN 중복 설명 |
| 3 | pipeline, tests, DAG, RUNBOOK | 롤백·중복·늦은 환불 테스트 개별 실행; 원인과 기대값 기록 | 재실행 안전성과 체크포인트 위치 설명 |
| 4 | benchmark, profile | 10만/20만 행을 다른 결과 파일에 측정; 시간·메모리 비교 | 제한된 측정에서만 결론을 내리고 dtype/chunk 설명 |
| 5 | JSONB, search, semantic, storage | EXPLAIN 읽기; 잘못된 의미 검색 결과 분석; Redis TTL 확인 | 저장소 역할과 ANN recall/속도 절충 설명 |
| 6 | PORTFOLIO, VERIFICATION | 테스트 DB에서 규칙 하나 수정하고 회귀 확인; 5분 시연 3회 | 코드를 보며 설계·한계·검증을 자기 말로 설명 |

학습 노트는 매일 ‘예상 결과 / 실제 결과 / 차이의 원인 / 내 말로 설명’ 네 줄로 작성합니다. 알 수 없는 코드는 복사하여 외우기보다 가장 작은 입력으로 실행합니다. 실패 주입은 테스트 전용 DB에서 수행하고 완성된 기준 결과를 별도로 보관합니다.

6주 종료 기준은 모든 기술 이름을 외우는 것이 아닙니다. 주문 한 건의 처리 흐름, 잘못된 JOIN의 문제, 트랜잭션의 역할, 늦은 환불 처리, 테스트 범위, 측정의 한계를 구체적 예로 설명할 수 있어야 합니다.
